# 数据架构演进：静态资产 vs Cloudflare D1

> 2026-08-12 评估。结论先行：**当前规模不需要 D1，静态资产方案可支撑数千期；D1 反而更受限。** 本文给出数据与迁移路径，供将来真正需要时使用。

## 一、现状：每期 1 个静态 JSON

```
web/public/
├── index.json                    # 全库索引（~10KB，11 期）
├── episodes/<id>/bilingual.json # 单期双语数据（100–500KB）
└── sitemap.xml / robots.txt      # SEO
音频 → RustFS（自建 S3，不走 Cloudflare）
```

新增一期 = 本地跑流水线 → `sync_web.py` 同步 → `wrangler deploy`（增量上传，按 hash 去重）。

## 二、Cloudflare Workers 静态资产限额（2025-09 更新后）

| 指标 | 限额 | 本项目实际 |
|---|---|---|
| 单文件大小 | 25 MiB | bilingual.json 最大 ~500KB，余量 50× |
| 文件总数 | **20,000**（免费）/ 100,000（付费） | 每期 1 个文件 → 可支撑 **2 万期** |
| 总大小 | **无上限**（官方未设总量 cap） | — |
| 流量/存储费 | 静态资产服务免费，不占 Workers 请求额度 | — |

**结论：静态方案在免费额度下可支撑约 2 万期，不存在"节目多了就传不上去"的问题。** 音频早已分流到 RustFS，不占 CF 任何额度。

## 三、D1 的限额（对比）

| 指标 | 限额 | 对本项目的含义 |
|---|---|---|
| 单库大小 | 10 GB（付费）/ **500 MB（免费）** | 免费档只够 ~1000 期（按 500KB/期），**比静态资产更小** |
| 单行大小 | 2 MB | bilingual.json 500KB 可存，但 1.5MB+ 的大期会超限 |
| 免费档读写 | 5M 行读 / 100K 行写每天 | 全站搜索会吃读额度 |

**结论：把 bilingual.json 塞进 D1 是倒退**——免费档容量更小、有行大小上限、还要写 Worker API 路由。

## 四、什么时候才值得上 D1 / 数据库

只有出现以下需求之一，才考虑迁移（按优先级）：

1. **服务端全文搜索**（跨期搜句子/关键词，现在只能前端过滤 index.json 的标题）
2. **动态筛选/分页**（按 level/category/时长服务端查询）
3. **多端进度同步**（现在收听进度只存 localStorage，换设备不共享）
4. **不部署就加内容**（D1 可随时写，静态资产要 deploy——但 deploy 已脚本化，1 分钟搞定，收益有限）

## 五、若将来迁移：推荐形态（元数据 D1 + 内容 R2）

```
D1 表 episodes(id, podcast, title_zh, title_en, category, level, pub_date, duration, pairs_count, image, audio_url)
D1 表 pairs(episode_id, idx, start, end, en, zh)   ← 逐句可查，服务端搜索
R2 桶存 bilingual.json 原样（或干脆不存，直接查 D1 拼装）
```

- 前端 `index.json` 改为调 Worker API `/api/episodes`；详情页调 `/api/episodes/:id`
- 迁移脚本：`scripts/migrate_to_d1.py` 读本地 episodes/ 批量 upsert（~1000 行/批）
- 音频维持 RustFS 不动

## 六、本次已做的配套优化

- **SEO**：meta/OG/Twitter/JSON-LD（WebSite/ItemList/PodcastSeries/PodcastEpisode）、`sitemap.xml`（`?id=` 形态，router 兼容）、`robots.txt`、路由级 title/description/canonical
- **统计**：Cloudflare Web Analytics beacon 已埋（token 待填，见 index.html 注释）
- **响应式**：详情页 Hero 移入 48rem 阅读列，与双语区对齐；播放条小屏防溢出
